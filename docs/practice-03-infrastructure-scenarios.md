## INF-01: A Managed Rule Blocks Valid Requests

**Format:** Single answer. **Focus:** Safe WAF tuning.

A public document-processing API uses AWS WAF. After a managed rule-group update, legitimate uploads receive blocks. WAF logs identify one subrule matching an expected application field. Other rules are still stopping validated attacks, and there is no evidence that the entire rule group is unsuitable. The team must restore legitimate uploads while retaining unrelated protections and collecting evidence for a narrow long-term adjustment.

Which action best meets those constraints?

- A. Change every rule in the web ACL to Count indefinitely.
- B. Add a highest-priority Allow for the entire upload path so no later rule evaluates those requests.
- C. Apply a targeted action override or narrowly scoped adjustment for the identified rule, validate representative traffic, and retain monitoring and the other protections.
- D. Raise the application's security-group limits because security groups interpret the blocked HTTP field.

**Answer: C.** The evidence identifies a specific rule interaction. A targeted, verified change minimizes the protection removed while allowing investigation.

**Why the other choices fail:** A also disables enforcement for unrelated attacks. B can bypass subsequent WAF checks for every request on that path, not just the false positive. D targets a network control that does not parse this application field.

**Verify:** Test legitimate and malicious requests that resemble the affected traffic, inspect rule metrics/logs, and account for configuration propagation. Count mode observes; it does not itself prove a request is safe.

[WAF testing and tuning](https://docs.aws.amazon.com/waf/latest/developerguide/web-acl-testing.html).

## INF-02: The Firewall Sees Only Half The Connection

**Format:** Single answer. **Focus:** Stateful inspection and routing symmetry.

A company centralizes Network Firewall in an inspection VPC connected through Transit Gateway. After a route change, an application can send initial connection packets, but sessions fail. Captured path evidence shows forward traffic traversing the firewall endpoint and return traffic taking a different path. The approved security requirement is stateful inspection in both directions, not simply connectivity at any cost.

Which change is most appropriate?

- A. Add broad stateful allow rules while preserving the asymmetric path.
- B. Route both directions directly between application networks, bypassing inspection.
- C. Broaden return-traffic NACL rules while leaving the observed return route outside the inspection path.
- D. Correct forward/return routing through the inspection attachment and use appropriate Transit Gateway appliance-mode configuration to keep each flow on the required inspection path.

**Answer: D.** A stateful engine needs the related traffic on the supported symmetric path. The supplied evidence points to routing, not missing application authorization.

**Why the other choices fail:** A does not make missing return packets visible to the stateful engine. B restores a route by abandoning mandatory inspection. C changes a packet filter without correcting the demonstrated path asymmetry.

**Verify:** Trace both directions, including NAT and subnet routes where present. Check that stateless handling forwards the required traffic into stateful inspection rather than allowing one direction to bypass it.

[Network Firewall asymmetric routing](https://docs.aws.amazon.com/network-firewall/latest/developerguide/asymmetric-routing.html).

## INF-03: A Model Is Allowed To Suggest, Not Authorize

**Format:** Single answer. **Focus:** GenAI tool and tenant boundaries.

A support application uses a language model to summarize customer documents and suggest operations. An API backend executes suggested tool calls using a role that can read records for all tenants. A malicious document instructs the model to request a different tenant's record. The tool call includes a tenant identifier generated by the model. Content filtering is already enabled, but the application does not independently check tool authorization.

Which change most directly protects the data boundary?

- A. Add a stronger system prompt and treat any resulting tool request as authorized.
- B. Have a trusted tool broker validate action/resource access against the authenticated user's tenant and permissions before execution, rejecting untrusted tenant overrides.
- C. Increase model capacity so it is less likely to follow malicious instructions.
- D. Encrypt the shared database with KMS and remove application authorization checks.

**Answer: B.** The security boundary must be enforced by trusted application logic, not by text generated from potentially hostile input.

**Why the other choices fail:** A and C may affect model behavior but do not establish a deterministic authorization boundary. D protects storage while the authorized backend role can still read and leak plaintext across tenants.

**Verify:** Test malicious document instructions, forged tool arguments, and ordinary legitimate requests. Scope tool capabilities and credentials as well as enforcing user-level access. Log decisions without exposing sensitive document content unnecessarily.

[Review GenAI controls in the study guide](03-infrastructure-security-study-guide.md).

## INF-04: Connected Devices Cannot Receive Commands

**Format:** Multiple response. **Select TWO.** **Focus:** IoT action/resource distinctions.

A device named `sensor17` already connects with its own valid certificate and publishes telemetry successfully. It now needs to subscribe to and receive commands on exactly `fleet/sensor17/commands`. Its policy has Connect and telemetry Publish permissions but no command Subscribe or Receive permissions. Certificate attachment and transport connectivity are known to be healthy. It must not gain access to other devices' command topics.

Which two permissions are needed for the stated subscription/receive path?

- A. `iot:Publish` on every topic under `fleet/*`.
- B. `iot:Receive` on a `topicfilter/fleet/sensor17/commands` resource.
- C. `iot:Subscribe` on the appropriate `topicfilter/fleet/sensor17/commands` ARN.
- D. `iot:Connect` on every device's client ARN.
- E. `iot:Receive` on the appropriate `topic/fleet/sensor17/commands` ARN.

**Answer: C and E.** Subscription authorization refers to the topic filter; message-receive authorization refers to the topic. Both must be scoped to the intended device path.

**Why the other choices fail:** A authorizes sending, not receiving commands, and is unnecessarily broad. B uses the wrong resource category for Receive. D expands connection identity without fixing Subscribe or Receive.

**Verify:** Test the device's own command path and a neighboring device's path. Do not assume a successful MQTT connection grants every later messaging operation.

[IoT publish/subscribe policy resources](https://docs.aws.amazon.com/iot/latest/developerguide/pub-sub-policy.html).

## INF-05: Fix The Fleet Without Reintroducing The Vulnerability

**Format:** Ordering. **Use all four steps.** **Focus:** Image lifecycle and controlled rollout.

Inspector identifies a vulnerable package baked into the launch image of an autoscaled application. The package fix is available. The organization requires a tested replacement image, a canary, and verified fleet replacement. Updating only running instances would allow newly launched instances to reintroduce the issue. Immediate incident containment, if required, is handled separately.

Order the durable remediation steps.

- A. Roll out the validated launch configuration through controlled replacement, then inventory remaining old instances/images and verify vulnerability status.
- B. Build a candidate image using the approved patch and required hardening baseline.
- C. Launch a canary using the tested candidate and validate real application behavior and security telemetry before approving fleet rollout.
- D. Scan and test the candidate image, confirming the targeted package fix and checking for regressions.

**Answer: B -> D -> C -> A.**

**Reasoning:** B produces the corrected artifact. D checks it before use as the approved candidate. C tests workload behavior in the required canary stage. A replaces the fleet and proves that old vulnerable capacity is not silently left behind or relaunched.

**Closest wrong sequence:** Patch running instances -> declare complete misses the persistent image/launch configuration. A vulnerability scanner detects exposure; it does not itself update every affected image or guarantee deployment success.

[Review hardened image and patching workflows](03-infrastructure-security-study-guide.md).

## INF-06: Match A Control To Its Actual Boundary

**Format:** Matching. **Use each response once.** **Focus:** Network and browser control scope.

A developer proposes using one control for every connectivity issue. The security review separates four requirements. Match each to the most appropriate mechanism; other controls may still be needed alongside it.

| Requirement | Context |
| --- | --- |
| 1 | Allow an application tier to initiate connections to a database tier using stateful instance-interface filtering |
| 2 | Apply explicit, ordered subnet-level network allow/deny rules and account for return ports |
| 3 | Give VPC clients a private endpoint to a supported service with endpoint security-group controls |
| 4 | Tell browsers which permitted cross-origin requests/responses may be used, without granting object access |

Responses:

- A. S3 CORS configuration
- B. Interface VPC endpoint
- C. Network ACL
- D. Security group

**Answer: 1-D, 2-C, 3-B, 4-A.**

**Reasoning:** D is stateful and uses allowed rules rather than ordered explicit denies. C is stateless, so both directions need consideration. B changes the network access path but does not replace IAM. A governs browser cross-origin behavior; it is neither an IAM grant nor protection against a non-browser client.

**Verify:** Test network reachability and authorization separately. A browser CORS failure can coexist with a successful command-line request, while an available endpoint can still return AccessDenied.

[Review packet paths](00-aws-security-foundations-for-beginners.md#packet-paths-and-inspection-basics) and [browser boundaries](00-aws-security-foundations-for-beginners.md#edge-browser-and-device-basics).
